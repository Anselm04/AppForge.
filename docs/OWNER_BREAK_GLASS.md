# AppForge Owner Break-Glass Recovery Protocol

This protocol exists so the owner can regain control of AppForge after account lockout, device loss, credential compromise, malicious automation, provider failure, or a major security incident without weakening normal security.

## Design principles

1. Normal access and emergency recovery are separate.
2. No single password, phone, device, provider, GitHub account, or encryption key may be the only recovery path.
3. Break-glass credentials are never used for routine development.
4. Recovery secrets are never stored in this repository, issues, pull requests, logs, screenshots, prompts, or CI artifacts.
5. At least two independent recovery methods must exist for the owner.
6. At least one recovery method and one copy of the backup decryption key must be available outside GitHub.
7. Recovery access should be tested periodically without exposing secret values.
8. After break-glass use, affected credentials must be rotated before normal operations resume.

## Owner recovery kit

Maintain the following outside GitHub in at least two controlled locations. One may be a reputable password manager; one should be offline or otherwise independent.

- GitHub account recovery codes.
- A spare phishing-resistant passkey or hardware security key.
- Off-site backup encryption passphrase or recovery key.
- Off-site storage account recovery information.
- Domain registrar recovery information and MFA recovery codes.
- Supabase owner/recovery access information.
- Fly.io owner/recovery access information.
- Stripe owner/recovery access information.
- DNS provider recovery information.
- Password-manager emergency/recovery information.
- A printed or offline copy of this protocol and the disaster-recovery runbook.
- The latest known-good production commit SHA, updated periodically.

Do not put the actual secret values, recovery codes, seed phrases, private keys, API keys, passwords, or passphrases in this repository.

## Recommended owner authentication

For privileged accounts:

- Prefer passkeys or FIDO2/WebAuthn hardware security keys.
- Keep at least two independent authenticators.
- Keep one authenticator away from the daily-use device and normal workspace.
- Retain provider recovery codes offline.
- Avoid SMS as the only recovery mechanism.
- Use unique passwords generated by a password manager where passwords are still required.

## Production release control

Production deployment to Fly.io is manual. A green `CI Pipeline` run on `main` does not deploy anything. The owner starts `Deploy Production` explicitly from GitHub Actions (`workflow_dispatch` on `main`). That workflow re-validates the exact current `main` SHA (lint, typecheck, tests, e2e, build) and refuses stale SHAs before any Fly step runs. During an incident, simply not dispatching the workflow keeps production on the last released version; no workflow edits are needed to pause releases.

### Project intake kill switch

`projects.create` and `POST /api/generate` build every product contract deterministically from the user's prompt. When a model provider is configured, an optional enrichment step can only add schema-valid items to that contract. If enrichment ever misbehaves during an incident, set `APPFORGE_CONTRACT_LLM_ENRICHMENT=off` in the runtime environment. Intake then uses only the deterministic prompt-specific contract, with no redeploy of code needed. Prompts that cannot be classified return a structured clarification (question plus choices) instead of creating or charging a project.

## Emergency decision tree

### Case A: Daily device is lost or unavailable

1. Do not weaken account security to regain convenience.
2. Use the spare passkey/hardware key or provider recovery code.
3. Sign in from a trusted clean device.
4. Revoke the lost device/session where the provider supports it.
5. Verify GitHub, Supabase, Fly.io, Stripe, DNS, and backup-storage account activity.
6. Rotate any credential that may have been exposed on the lost device.

### Case B: GitHub account is locked but not believed compromised

1. Use GitHub's configured recovery method from a trusted device.
2. If GitHub is temporarily unavailable, retrieve the newest verified off-site AppForge recovery package.
3. Verify the encrypted backup checksum/HMAC and decrypt it using the separately retained key.
4. Restore the Git bundle into clean local storage or replacement source control.
5. Do not deploy anything until GitHub/replacement source control access and the trusted SHA are verified.

### Case C: GitHub account may be compromised

1. Treat the current GitHub repository state as untrusted.
2. Stop or disable production deployment using the safest available provider-level control.
3. Preserve evidence: suspicious SHAs, times, workflow runs, account alerts, sessions, deployments, and affected credentials.
4. Recover GitHub using an independent owner recovery path.
5. Revoke suspicious sessions, tokens, keys, apps, and credentials.
6. Rotate GitHub, Fly.io, Supabase, Stripe, database, webhook, AI-provider, DNS, and backup credentials that may have been exposed.
7. Retrieve the newest independent off-GitHub recovery copy created before the compromise window.
8. Verify checksum/HMAC, decrypt, run `git bundle verify`, clone cleanly, and run `git fsck --full --strict`.
9. Compare the recovered SHA with known successful CI/security/deployment records.
10. Re-run the full CI, security, build, customer-flow, and production verification gates before service restoration.

### Case D: GitHub and the normal backup artifact are both unavailable

1. Use the independent off-GitHub encrypted backup target.
2. Use the separately retained decryption key.
3. Restore into a clean environment.
4. Recreate source control if necessary.
5. Re-establish repository protections before allowing normal development.
6. Restore only known-good code and rotate privileged credentials before deployment.

### Case E: Backup encryption key is unavailable

The design must prevent this from becoming a permanent lockout.

- Maintain two controlled copies of the decryption key outside GitHub.
- Never rotate or destroy the previous key until all retained backups encrypted under it have either expired or been re-encrypted and independently verified.
- Record key-rotation dates without recording key material.
- Test decryption from an independent recovery location after any key rotation.

## Provider recovery order

For a major incident, recover in this order unless incident conditions require otherwise:

1. Owner identity and password-manager access.
2. Domain registrar and DNS ownership.
3. Independent backup storage and decryption capability.
4. Source control and repository protections.
5. Supabase/database/auth/storage state.
6. Fly.io runtime/deployment capability.
7. Stripe billing/webhook configuration.
8. AI-provider and other supporting service credentials.
9. Production deployment from an exact known-good SHA.
10. Customer-flow and revenue-path acceptance verification.

## Break-glass production rule

Emergency access does not mean emergency bypass.

Even during recovery:

- Never deploy an unverified commit merely to restore service quickly.
- Never disable security checks permanently to make recovery easier.
- Never reuse known-compromised credentials.
- Never allow an AI agent to select a trusted recovery point without human verification of the SHA and recovery evidence.
- Never expose recovery secrets to a PR, issue, AI prompt, CI log, or generated artifact.

## After emergency access is used

Before returning to normal operation:

1. Rotate credentials used or exposed during recovery.
2. Revoke temporary sessions and emergency tokens.
3. Re-enable/verify normal branch, environment, and deployment protections.
4. Verify the newest off-site backup can be downloaded, authenticated, decrypted, and restored.
5. Record the incident timeline without secret values.
6. Record the trusted production SHA.
7. Verify owner recovery methods still work.
8. Replace any recovery code or hardware key that was lost, exposed, or consumed.

## Recovery testing cadence

At least quarterly, and after any material authentication/provider change:

- Confirm two independent owner authentication/recovery paths exist.
- Confirm recovery codes are accessible offline.
- Confirm the backup decryption key is accessible from an independent recovery location.
- Confirm an off-site recovery archive can be downloaded and decrypted.
- Confirm a clean Git restore works.
- Confirm the latest known-good SHA is recorded.
- Confirm provider recovery documentation is current.

A secure system must be difficult for an attacker to enter and predictable for the legitimate owner to recover.
