# Flutter + Node target

`flutter-node` extends the existing stack registry and generation pipeline. Its maturity remains conservative: the shared target is structural until each stronger state is backed by reproducible evidence. Explicit Flutter + Node requests select it; ordinary mobile defaults remain unchanged.

The artifact contains a Flutter client at `lib/`, a TypeScript backend at `server/src/`, and one public API contract at `shared/contracts/product-api.json`. Flutter bundles that contract as an asset; the backend loads it at startup. Backend build output belongs to `build/server/`. Root Node scripts and separate Flutter scripts keep component checks distinct.

The infrastructure shell supplies health transport and a consistent error envelope. It does not supply product behavior, authentication, a database, or reservation integrations. The contract explicitly marks authentication as unimplemented. Product generation must implement these requirements, and scaffold merging does not fill missing product entrypoints with a generic application.

Flutter configuration merging preserves product dependencies and assets while adding required infrastructure entries. Structural validation rejects disconnected manifests and malformed shared contracts. Backend startup contracts are checked separately from the primary mobile runtime. Source checks are not runtime certification.

The trusted qualification fixture compiles the backend, resolves Flutter dependencies, runs the Flutter shell test, and retains evidence. Ubuntu additionally compiles the web target. The Android lane extends that same trusted fixture through the existing Flutter/Android toolchain: it records Java, Android SDK and `flutter doctor` evidence, builds and hashes a real debug APK, boots an API 35 emulator, installs and launches the APK, verifies the app process, starts the real Node backend, and runs the Flutter integration test through `adb reverse` before capturing a screenshot. The workflow does not auto-accept Android SDK licenses; missing accepted-license/tooling state remains a real failure or external dependency.

The macOS lane uses legitimate Xcode infrastructure, boots an available iPhone simulator, builds the iOS simulator target, runs the same integration harness against the real Node backend, and captures evidence. A green trusted-fixture lane proves only the exact runner/toolchain/scaffold/interactions exercised by that run; it does not certify arbitrary generated customer products.

Still separate and uncertified until independently proven are generated-product authentication and persistence, release signing, AAB/Google Play preparation, Apple archive/export/provisioning, push notifications, deep links, background jobs, voice, reservation-provider behavior, production deployment, store release, and the complete Golden Product customer journey. Generated backend credentials remain server-side; only the public API address belongs in Flutter configuration. Production mobile requests must use HTTPS.
